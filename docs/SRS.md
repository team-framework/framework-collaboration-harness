# Framework Collaboration Harness — SRS

## 1. 목적

이 저장소는 Framework 팀의 GitHub 협업 흐름을 **강제하지 않고 안내하는 하네스**예요. 팀원과 AI 에이전트가 같은 이슈·브랜치·커밋·PR 기준을 읽고, 실제 GitHub 상태에 맞춰 Discord 알림을 받을 수 있게 해요.

## 2. 범위

### 포함

- AI 에이전트가 읽는 이슈·커밋·PR SKILL과 `AGENTS.md`
- GitHub Web과 `gh`/`git` CLI에서 함께 쓸 수 있는 이슈 폼·PR 템플릿
- 다른 저장소로 템플릿과 SKILL을 설치하는 스크립트
- 담당자가 비어있는 이슈의 담당자를 생성자로 자동 지정
- GitHub 활동을 기준으로 하는 개인별 Discord 알림과 일일 팀 요약
- Discord 스레드 대화를 원인·진행 과정·결론으로 정리하는 명령
- 전용 read-only GitHub App과 저장소별 Discord 실시간 활동 피드
- Discord Bot 온라인 상태 유지용 Gateway 실행 도구

### 제외

- 제목·브랜치·커밋 형식을 CI로 차단하는 컨벤션 검사
- 메일 알림
- Discord 메시지를 읽었는지 또는 버튼을 눌렀는지로 작업 완료를 판단하는 기능
- Bot 토큰·Discord ID·채널 ID 같은 민감 정보의 저장소 저장

## 3. 협업 기준

- 작업 유형은 `feat`, `fix`, `chore`, `refactor` 순서로 선택해요.
- 이슈·브랜치·PR은 이슈 번호를 연결하고, 설명은 한국어로 작성해요.
- 브랜치 형식은 `<type>/<영문-작업명>/#<issue-number>`이에요.
- 커밋 형식은 `<type>: <한국어 작업 설명>`이에요.
- PR 형식은 `<type>: <영문-작업명>/#<issue-number>`이고, 처음에는 항상 Draft로 만들어요.
- 일반 저장소의 `main`은 직접 push하지 않고, 최소 1명 승인과 필수 검사를 통과한 뒤 병합해요. 이 규칙의 강제는 GitHub Ruleset이 담당해요.

## 4. 기능 요구사항

### FR-1. 안내 및 템플릿

1. 에이전트는 `AGENTS.md`에서 작업 종류별 SKILL을 찾을 수 있어야 해요.
2. SKILL은 GitHub Web과 `gh`/`git` CLI 각각에서 같은 결과를 만들 수 있게 안내해야 해요.
3. 설치 스크립트는 대상 저장소에 이슈 폼, PR 템플릿, SKILL, 대상별 `CODEOWNERS` 설정을 복사해야 해요.

### FR-2. 이슈 기본값

1. 이슈 폼은 작업 유형을 선택할 수 있어야 해요.
2. 담당자가 없는 이슈가 생성되면 생성자를 담당자로 지정해야 해요.
3. 담당자가 바뀌면 해당 담당자에게 적용되는 알림 기준 시각도 재설정해야 해요.
4. 마감일은 따로 두지 않고, 정해진 작업 중단 의심 시간을 주기로 Discord Bot이 재촉 알림을 보내요.

### FR-3. PR 흐름

1. PR은 처음부터 Draft로 생성하고, 작성자의 작업이 마무리되었을 때만 Ready for review로 전환해야 해요.
2. 대상 저장소는 기본 리뷰 팀을 `.github/CODEOWNERS`에 지정해야 해요. Draft PR에는 자동 리뷰 요청을 보내지 않고, Ready for review 전환 시에만 Code Owner 팀에 자동 리뷰를 요청해야 해요.
3. Code Owner로 지정된 GitHub Team은 공개 상태이고 대상 저장소에 Write 권한이 있어야 해요.
4. GitHub Ruleset을 적용하는 저장소는 `main` 직접 push를 막고, 승인과 필수 검사를 병합 조건으로 둘 수 있어야 해요.

### FR-4. Discord 알림

1. 알림은 담당자 개인별 Discord 비공개 채널에 Bot이 직접 멘션해 전송해야 해요.
2. 알림은 Discord 확인 여부가 아니라 GitHub의 실제 상태와 마지막 활동 시각으로 판단해야 해요.
3. 알림 본문에는 대상, 필요한 다음 행동, 경과 시간을 포함해야 해요. 예: “이슈가 할당된 뒤 5시간째 연결된 브랜치가 없어요.”
4. 다음 상태를 감지할 수 있어야 해요.
   - 이슈가 할당된 뒤 5시간 동안 브랜치 없음
   - 브랜치 생성 뒤 10시간 동안 커밋 없음
   - 마지막 커밋 뒤 24시간 동안 새 커밋과 PR이 모두 없음
   - 리뷰 요청 뒤 5시간 동안 응답 없음
   - 승인 뒤 1시간 동안 병합 없음
   - 변경 요청 뒤 5시간 동안 새 커밋 없음
5. 매일 오전 9시(Asia/Seoul)에 처리할 PR, 열린 지 24시간이 넘은 이슈(경고), 열린 지 48시간이 넘은 이슈(심각), 막힌 작업을 팀 채널에 요약해요.

### FR-5. Discord 스레드 정리

1. 메시지에서 시작했거나 독립 생성한 스레드 안에서 `/스레드-정리` 명령을 실행할 수 있어야 해요.
2. 스레드 메시지를 시간순으로 읽고 `3줄 요약(문제 상황·과정·상태/결론) → 타임라인 → 다음 작업`으로 한국어 요약해야 해요. Discord Markdown 헤딩(`#`, `##`, `###`)으로 제목과 3줄 요약을 계층화하고, 타임라인에는 중요한 확인·시도·결정만 발생 시각순으로 표시해야 해요.
3. 요약은 `# {스레드명} 스레드 정리` 제목으로 시작하고 이모티콘을 넣지 않아야 해요.
4. 메시지에서 시작한 스레드는 부모 채널의 시작 메시지에 답글로 남겨야 해요.
5. 독립 생성한 스레드는 부모 채널에 스레드 작성자를 멘션한 일반 메시지로 남겨야 해요.
6. 답글 또는 멘션 알림은 스레드 작성자에게 전송해야 해요.
7. 포럼·미디어 게시물과 일반 채널에서는 명령을 처리하지 않고 사용자에게 지원 범위를 알려야 해요.

### FR-6. 저장소별 GitHub 활동 피드

1. 지연 알림과 독립된 webhook 서비스로 동작해야 해요.
2. `innolive-client`, `innolive-server`, `innolive-ai`, `framework-collaboration-harness`만 허용해야 해요.
3. Discord `github` 카테고리 아래 저장소별 채널과 PR별 전용 채널로 라우팅해야 해요.
4. PR마다 `저장소명-pr-번호` 채널을 하나만 만들고, 해당 PR의 상태·커밋·댓글·리뷰·코드 라인 댓글·리뷰 스레드만 그 채널에 전달해야 해요.
5. 서비스 시작 시 현재 Open PR과 그 커밋·댓글·리뷰·코드 라인 댓글 기록을 시간순으로 중복 없이 동기화해야 해요.
6. 댓글·리뷰·승인·변경 요청·병합·Close 등 활동 종류별 embed 색상을 구분해야 해요.
7. PR 병합 또는 Close 알림에는 채널 닫기 버튼을 표시하고, 채널 관리 권한이 있는 사용자가 누르면 해당 닫힌 PR 채널만 삭제해야 해요.
8. 이슈·PR·일반 댓글·리뷰·코드 라인 댓글·리뷰 스레드·push·Check·Actions·배포·Release 활동을 전달해야 해요.
9. 삭제된 댓글의 본문은 Discord에 다시 보존하지 않아야 해요.
10. GitHub App은 쓰기 권한 없이 필요한 repository permission만 Read-only로 사용해야 해요.
11. `X-Hub-Signature-256`을 검증하고, 허용되지 않은 저장소와 잘못된 서명을 거부해야 해요.
12. `X-GitHub-Delivery`와 동기화 기록 ID를 기준으로 중복을 방지하고, Discord 장애 중에는 영속 큐에 남겨 재전송해야 해요.

## 5. 비기능 요구사항

- 문서와 알림은 기본적으로 한국어와 부드러운 `~요` 말투를 사용해요.
- Bot 토큰, Discord 사용자·채널 ID, 팀별 설정은 환경변수 또는 GitHub Secret/Variable로만 제공해요.
- 개인 알림은 지정한 사용자만 멘션하고 `@everyone`·역할 멘션을 허용하지 않아요.
- GitHub 활동 본문의 사용자·역할·`@everyone` 멘션은 Discord 멘션으로 해석하지 않아요.
- 일일 팀 요약은 설정된 Framework Team 역할만 멘션할 수 있어요. 역할 ID는 `DISCORD_TEAM_ROLE_ID` 환경변수로 제공하고, 그 외 역할·`@everyone` 멘션은 허용하지 않아요.
- Discord Gateway 연결은 끊기면 재연결하고, 장기 운영은 로컬 터미널이 아닌 지속 실행 환경에서 동작해야 해요.
- 알림 판별은 재실행해도 중복 발송하지 않도록 상태를 저장해야 해요.
- AI에 전달하기 전에 작성자 이름과 사용자 멘션을 익명화하고, 요청 저장을 비활성화해야 해요.
- Discord 메시지 원문과 AI 요약 결과를 서버 로그에 기록하지 않아야 해요.

## 6. 수용 기준

- 새 이슈, 브랜치, 커밋, Draft PR을 SKILL 예시대로 Web과 CLI에서 각각 만들 수 있어야 해요.
- Draft PR을 만들었을 때는 Code Owner에게 리뷰 요청이 전송되지 않고, Ready for review 전환 뒤에만 전송되어야 해요.
- 담당자 없는 이슈를 만들면 생성자가 자동으로 지정되어야 해요.
- 알림 판별기는 실제 GitHub 데이터로 위의 일곱 상태를 계산하고, 한 상태당 담당자에게 한 번만 알려야 해요.
- 테스트 알림은 지정 사용자만 멘션하며 민감 정보가 저장소나 로그에 남지 않아야 해요.
- `/스레드-정리`는 스레드명과 원인·진행 과정·결론을 생성하고, 시작 방식에 맞게 원본 메시지 답글 또는 부모 채널 멘션 메시지로 전송해야 해요.
- `main` 보호가 필요한 저장소에서는 Ruleset으로 직접 push와 조건 미충족 병합이 차단되어야 해요.
- GitHub 공식 HMAC-SHA256 테스트 벡터와 저장소별 라우팅 테스트를 통과해야 해요.
- Discord가 일시적으로 실패하면 webhook은 이미 큐에 수락되고, 복구 뒤 같은 delivery를 한 번만 전송해야 해요.
